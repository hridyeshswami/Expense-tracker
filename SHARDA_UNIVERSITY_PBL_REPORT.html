5. PROBLEM STATEMENT

5.1 Background & Context

When students enter university, they assume complete independent responsibility for their personal finances for the first time. They operate with finite financial inflows—typically periodic monthly parental allowances, government education stipends, scholarships, or modest part-time wages. These constrained funds must cover non-negotiable educational survival expenses (hostel rent, mess fees, bus passes, textbooks, and semester exam fees) alongside discretionary social spending.

In contemporary cashless ecosystems, the exponential rise of tap-and-pay UPI micro-transactions has decoupled the physical "pain of paying" (Soman, 2001). Frictionless digital spending causes ₹40 snacks, ₹30 transit rides, and ₹150 food deliveries to accumulate invisibly, frequently leaving students with zero balance halfway through the month.

5.2 Why this Topic Was Selected

  1. Severe Youth Financial Distress: Over 60% of university undergraduates report running completely out of funds 10 to 15 days before month-end, inducing acute psychological and academic anxiety.
  2. Failure of Commercial Platforms: Mainstream commercial applications (YNAB, Monarch, Splitwise) are designed for corporate salaried adults possessing stable incomes and mortgages. They require 8 to 12 form fields per transaction, charge high monthly subscriptions ($8–$15/month), and demand invasive bank credential syncing.
  3. Engineering & Academic Rigor: Developing an intelligent student expense tracker represents an authentic Project-Based Learning endeavor uniting frontend engineering, 3NF relational database architecture, algorithmic mathematics, and behavioral economics.

5.3 Specific Problems Addressed

  • Logging Fatigue: Reducing entry overhead from 10 tedious form fields to an instant 3-step modal taking under 5 seconds.
  • Absence of Daily Guidance: Eliminating the guesswork of lump-sum balances by computing an algorithmic Safe-to-Spend Daily Limit.
  • Impulse Spending Blindness: Forcing conscious cognitive evaluation through binary Need vs. Want classification.
  • Unmonitored Subscription Leaks: Tracking silent recurring drains (mobile packs, streaming services, bus passes) with upcoming due-date alerts.
  • Data Privacy & Security: Preserving data sovereignty via a clean-slate, local-first architecture with Admin PIN protection (`admin123`).

7. PROJECT DESCRIPTION

7.1 Scope of Work

Student Expense Tracker is an all-in-one, responsive web application engineered specifically for university student personal finance. It provides a client-side Single Page Application (SPA) requiring zero setup while supplying an enterprise-grade 3NF relational backend (MySQL/SQLite) and RESTful PHP API services.

7.2 System Architecture Overview

The prototype follows a modular three-tier architecture:

  • Presentation Layer: Semantic HTML5, CSS3 Grid/Flexbox, and Chart.js canvases optimized for both desktop and mobile viewports.
  • Application & State Layer: Vanilla JavaScript object-oriented state manager (`StateManager`) and financial calculations engine (`calculations.js`).
  • Data Layer: Dual-tier persistence utilizing browser `localStorage` for zero-latency client execution, alongside a normalized 3NF MySQL relational database schema.

8. PROJECT MODULES: DESIGN / ALGORITHM

8.1 Module 1: Profile & Budget Initialization

Manages student baseline settings: Expected Monthly Allowance, Overall Monthly Spending Cap, Currency Denomination (`₹`), and Student Mode. Configured through the Settings tab or Admin modal.

8.2 Module 2: 3-Step Rapid Transaction Entry Engine

Streamlines recording into an ultra-fast 3-step modal taking under 5 seconds: Amount $\to$ Category $\to$ Need/Want & Payment Method.

8.3 Module 3: Need vs. Want Cognitive Tagging Engine

Needs % = ( Total Needs Expenses / Total Expenses ) × 100
Wants % = ( Total Wants Expenses / Total Expenses ) × 100

If Wants % exceeds 35%, an automated cognitive alert is rendered in the Insights panel to encourage immediate spending discipline.

8.4 Module 4: Dynamic Safe-to-Spend Daily Limit Algorithm

Effective Budget = ( Overall Budget > 0 ) ? Overall Budget : Monthly Income
Remaining Budget = Max( 0, Effective Budget - Total Spent This Month )
Days Remaining = Max( 1, Total Days In Month - Current Day Of Month + 1 )
Safe Daily Limit = Floor( Remaining Budget / Days Remaining )

This equation is self-correcting: overspending today automatically lowers tomorrow's daily limit, guaranteeing solvency through the final day of the month.

8.5 Module 5: Category Budget Health Monitoring Algorithm

Utilization Ratio (U) = ( Category Spent / Category Budget ) × 100
Status = [ U < 70%: Under Control (Green) ] | [ 70% ≤ U ≤ 95%: Warning (Yellow) ] | [ U > 95%: Exceeded (Red) ]

8.6 Module 6: Plain-Language Natural Insights Synthesizer

Synthesizes raw transactional metrics into readable advice (e.g., "You have ₹240/day safe to spend for the remaining 16 days this month.").

8.7 Module 7: Milestone Savings Goal Tracker

Calculates required monthly savings: $\text{Monthly Deposit} = \frac{\text{Target Amount} - \text{Saved Amount}}{\text{Remaining Months}}$. Renders animated progress bars.

8.8 Module 8: Recurring Subscriptions & Fixed Liabilities Desk

Maintains scheduled obligations (WiFi, mobile packs, mess fees) with automated due-date reminders and status badges.

8.9 Module 9: In-Browser Relational Database Workbench & SQL Console

An embedded inspection console displaying live 3NF table rows, column data dictionaries, SQL DDL schemas, live SQL query simulator, and a 1-click executable `.sql` dump generator.

8.10 Module 10: Admin Security & Role-Based Access Control

Gated with PIN `admin123`. Allows reviewers to view the prototype in read-only Viewer Mode while enabling administrators to add categories, record transactions, and initiate data resets.

10. RESULT & CONCLUSION

The Student Expense Tracker prototype was successfully engineered, rigorously verified, and deployed publicly on the Netlify cloud platform. Key innovations include:

  1. 100% Clean-Slate Initial State: Zero dummy data; the system initializes from absolute zero.
  2. Dynamic Daily Guidance: The Safe-to-Spend limit self-adjusts daily to prevent mid-month deficits.
  3. In-Browser Relational Workbench: Enables live SQL query execution and schema inspection directly within the browser shell.
  4. Zero Operating Cost: Built completely with free, open-source web technologies.

Conclusion: By prioritizing usability, cognitive nudges, and data privacy over corporate accounting complexity, the prototype effectively solves the challenge of student personal budgeting in a cashless economy.
